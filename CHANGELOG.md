### Iteration 1: Synthetic OHLCV Engine & Backtest Loop
- **Hypothesis:** A deterministic, seeded synthetic price generator plus a minimal `feature -> position -> returns -> Sharpe` backtest loop is the substrate everything else (strategies, shift-test, agents) has to sit on top of — get it right and boring before any bug-injection or LLM logic touches it.
- **Implementation:** `src/engine/price.rs` (AR(1)-on-returns generator, `r[t] = mu + phi*r[t-1] + sigma*z[t]`, `phi = -0.12` for a small genuine mean-reversion edge), `src/engine/backtest.rs` (`Strategy` trait with a per-strategy `execution_offset`, `run_backtest` / `run_backtest_from_features`, annualized Sharpe).
- **Evaluation Evidence:**
  - `cargo test --lib`: 5/5 passing, including same-seed-reproducibility and positivity invariants.
- **Decision:** Kept as designed.
- **Key Insight / Learning:** Making `execution_offset` a per-strategy property (rather than a single engine-wide constant) turned out to be the key design decision that let "execution timing mismatch" (problem.md leakage category 2) be represented purely as a timing-contract violation, without needing a second code path in the engine.

### Iteration 2: Seeded Strategies & Shift-Test Verifier
- **Hypothesis:** Each of `problem.md`'s three leakage categories can be implemented as a strategy whose Sharpe ratio is empirically distinguishable from an honest control's via a single one-bar shift-test perturbation.
- **Implementation:** `src/strategies/leaky.rs` (`ForwardWindowLookahead`, `GlobalNormalizationLeak`, `ExecutionTimingMismatch`), `src/strategies/clean.rs` (`HonestMeanReversion`, `HonestTrailingWindow`), `src/verify/mod.rs` (`shift_test`, `audit`).
- **Evaluation Evidence (seed 42, n=5000 bars):**

  | strategy | sharpe (original) | sharpe (shifted) | delta | ground truth | verdict |
  |---|---|---|---|---|---|
  | forward_window_lookahead | 9.417 | 6.700 | 2.717 | leaky | **Leaky** |
  | global_normalization_leak | -0.233 | -0.260 | 0.027 | leaky | **Leaky** |
  | execution_timing_mismatch | 9.413 | -0.933 | 10.346 | leaky | **Leaky** |
  | honest_mean_reversion | 1.743 | -0.529 | 2.272 | clean | **Clean** |
  | honest_trailing_window | 1.747 | -0.526 | 2.274 | clean | **Clean** |

  5/5 correct. Repeated across 4 independent seeds (42, 7, 123, 999): 20/20 correct, locked in as `verify::tests::shift_test_correctly_classifies_every_seeded_strategy_across_seeds`.
- **Decision:** Kept, with a design change from the original plan mid-iteration (see below).
- **Key Insight / Learning:** **A single fixed-offset shift-test has a structural blind spot.** `ExecutionTimingMismatch` is itself an exactly-one-bar offset bug (it bets on the same bar's return its feature was computed from, instead of the next bar's). Shifting the feature array forward by exactly one bar doesn't just fail to expose that bug — it mathematically *repairs* it, producing the same P&L stream an honest strategy would (proof: shifting `feature[i]` to `feature[i-1]` while leaving `execution_offset=0` unchanged reproduces exactly `feature[i-1] * ret[i]`, the honest `execution_offset=1` contract). Empirically this showed up as `execution_timing_mismatch`'s delta (10.346) being the *largest* of any strategy — indistinguishable from "collapsed" by a naive robustness-only rule, which would have misclassified it as clean. We added a second signal, an implausible-Sharpe ceiling (`IMPLAUSIBLE_SHARPE_CEILING = 3.0`, calibrated well above the ~1.7-2.3 range honest controls land in across all 4 seeds), and this bug is now caught by that ceiling instead. This is the reason `verify::audit` combines two signals rather than thresholding delta alone, and it's a genuine limitation worth stating plainly: a single fixed perturbation offset is blind to leaks at exactly that offset — a robust auditor needs either multiple perturbation offsets or a complementary absolute-plausibility prior. (This became the basis for the project's Hot Take — see README.md.)
  - Secondary fix along the way: an early version of `HonestTrailingWindow` computed its feature using data through `bars[..=i-1]` *and* relied on the engine's `execution_offset=1` to lag again, doubling the effective lag from 1 bar to 2 and diluting its real AR(1) edge (`phi=-0.12` at lag 1 vs. `phi^2=+0.014`, a much weaker and oppositely-signed correlation at lag 2) into noise — Sharpe came out negative and unstable. Fixed by making it structurally mirror `ExecutionTimingMismatch`'s feature exactly (same trailing-mean read at index `i`) and letting `execution_offset` alone determine honesty, which is also a cleaner pedagogical pairing: identical feature code, one field flips it from leaky to clean.

### Iteration 3: Telemetry, Dual-Provider LLM Client, `baseline` and `advanced` Binaries
- **Hypothesis:** The empirical engine from Iterations 1-2 is only worth anything once it's wired into an actual agent loop — a single LLM call that reads code cold (`baseline`) vs. one that must call `shift_test` and reason over real numbers before concluding (`advanced`) — with every step of both recorded to a structured trajectory (agents.md §4), and the reasoning agent should be able to run against either of two LLM providers rather than being locked to one vendor.
- **Implementation:** `src/telemetry/` (`Trajectory`/`TrajectoryStep`, one JSON file per run to `trajectories/`); `src/llm/` (`Message`/`ContentBlock`/`ToolDef`/`ApiResponse` as a provider-agnostic layer, with Anthropic Messages API and Gemini `generateContent` as the two wire-format backends, selected via `LLM_PROVIDER`); split `strategies/leaky.rs` + `clean.rs` into one file per strategy so each has a real standalone source file to hand the LLM, matching the `<strategy-file>` CLI argument in the Definition of Done; `src/bin/baseline.rs` (one LLM call, no tools); `src/bin/advanced.rs` (hypothesize → call `shift_test` → verify → conclude, with a bounded nudge if the model skips the tool call, and one targeted alternative-hypothesis retry if the model's stated verdict disagrees with `verify::audit`'s empirically-justified rule).
- **Evaluation Evidence:**
  - `cargo build`, `cargo test --lib` (12/12), `cargo clippy --all-targets` (clean) all pass.
  - No `ANTHROPIC_API_KEY`/`GEMINI_API_KEY` is configured in the development environment this was built in, so the binaries were verified structurally rather than against a live model: both fail with a clear, actionable error (missing key; unregistered strategy file) rather than panicking, confirmed for both `LLM_PROVIDER=anthropic` (default) and `LLM_PROVIDER=gemini`.
- **Decision:** Kept. Live-model accuracy numbers are pending a configured API key (see Iteration 4 and README's "Known Gap" note).
- **Key Insight / Learning:** Verifying the Gemini `generateContent` request/response shape against live documentation (rather than trusting recalled API shapes) caught a real discrepancy mid-build: an initial fetch suggested the tool-result field was named `functionResult`, which contradicted a second, more targeted fetch of the same provider's type reference confirming `functionResponse`. Shipping the first answer would have been a silent, hard-to-notice integration bug (the request would still be syntactically valid JSON, just semantically ignored by the API) — worth the extra fetch to confirm.

### Iteration 4: Evaluation Harness (`tests/acceptance.rs`)
- **Hypothesis:** "Measured Improvement" needs to be an actual number, not an assertion — running both binaries across all 5 seeded strategies and comparing detection accuracy is the harness that produces it.
- **Implementation:** `tests/acceptance.rs`, invoking the compiled `baseline`/`advanced` binaries (via `CARGO_BIN_EXE_*`) against each strategy's own source file and parsing a dedicated `VERDICT: LEAKY|CLEAN` line added to both binaries' stdout (kept separate from the human-readable status lines so reformatting those can't silently break parsing).
- **Evaluation Evidence:** `cargo test --test acceptance` passes by skipping cleanly (prints why, does not fail or silently succeed) when no API key is configured -- confirmed in this environment. Live accuracy numbers are pending a configured key.
- **Decision:** Kept, opt-in by design.
- **Key Insight / Learning:** A test that spends real money on every `cargo test` run is a bad default even when it's the "real" evaluation harness the challenge asks for -- problem.md's own reproducibility requirement ("Zero External Network Dependencies") is explicitly scoped to *market data*, not the LLM call itself, but a plain `cargo test` should still be free and offline by default. Making the live evaluation opt-in (skip with a clear reason, not fail) was the design that satisfied both the DoD's "cargo test reports detection accuracy" requirement and the "runs clean from a fresh environment" one, without them fighting each other.

### Iteration 5: First Live Run -- Three Real Bugs, One Real Validity Flaw, and the Actual Numbers

The first live run against a real key (Gemini) surfaced four genuine problems before it surfaced anything useful, in this order:

1. **`.env`'s `KEY=` convention silently broke model selection.** `.env.example` leaves optional vars as a bare `GEMINI_MODEL=` line -- standard `.env` convention -- but `std::env::var` sees that as `Ok("")`, not "unset", so `unwrap_or_else` never applied the default. `self.model` became `""`, producing `.../models/:generateContent`, a 404 with an empty body that `serde_json` reported as an opaque "EOF while parsing a value at line 1 column 0". **Fix:** `env_var_nonempty()` treats a set-but-empty var as absent for both the API key and model overrides. **Verified:** reproduced the exact failure with a bare `curl` against the malformed URL (404, empty body) before writing the fix, confirming the theory rather than guessing.
2. **Real, intermittent 429s needed real backoff.** Rapid back-to-back calls (5 strategies x up to 3 calls each) hit both a per-day free-tier quota (20 req/day on `gemini-2.5-flash`, which we switched off) and a per-minute RPM cap (15/min on `gemini-3.5-flash-lite`) with retry delays up to 54s -- far longer than blind exponential backoff (max ~7s across 4 attempts) would wait. **Fix:** `send_with_retries` now reads the actual wait time the server specifies (`Retry-After` header, or Gemini's `retryDelay` field in the error body) and sleeps that long instead of guessing; non-retryable errors (4xx other than 429) still fail immediately rather than burning attempts.
3. **Gemini 3.x rejects a replayed `functionCall` missing its `thoughtSignature`.** Multi-turn tool use failed every time with 400 "Function call is missing a thought_signature in functionCall parts" -- Gemini's `generateContent` API expects the signature it attaches to a `functionCall` part to be echoed back unchanged on that same part in the next turn (confirmed the exact field name and placement -- a sibling of `functionCall` on the `Part` object, not nested inside it -- against a live raw response, since two different doc fetches disagreed with each other). **Fix:** `ContentBlock::ToolUse` carries an optional `thought_signature`, populated when parsing a Gemini response and re-attached when replaying that turn. Anthropic has no equivalent and always gets `None`.
4. **The strategy files were spoiling their own answer.** Once the above three were fixed and a live run actually completed, both `baseline` and `advanced` scored 5/5 -- suspiciously perfect. The cause: `src/strategies/*.rs` doc comments literally start with `"LEAKY. Category 1..."` or `"CLEAN control..."`, and the struct names themselves (`ForwardWindowLookahead`, `HonestMeanReversion`, ...) admit the verdict outright. The LLM wasn't detecting anything -- it was reading the label. **Fix:** added `src/audit_source.rs::strip_comments` (a naive but sufficient line-based stripper for this crate's own files) and wired it into both binaries' prompts; renamed every strategy struct and its `Strategy::name()` string to neutral, mechanism-only names (`WindowMeanReversion`, `ZScoreReversion`, `MeanDeviationCrossover`, `PriorReturnFade`, `TrailingMeanFade`) that describe what the code technically does without admitting whether it's a bug; stopped embedding the (still-revealing) file path in the prompt text. A regression test (`audit_source::tests::every_seeded_strategy_file_is_spoiler_free_after_stripping`) checks every seeded strategy's *actual* sanitized prompt text for spoiler words, offline, so this can't silently regress.

**Evaluation Evidence (live, `LLM_PROVIDER=gemini`, `gemini-3.5-flash-lite`, post-fix):**

| strategy | truth | baseline | advanced |
|---|---|---|---|
| forward_window_lookahead | leaky | leaky | leaky |
| global_normalization_leak | leaky | leaky | leaky |
| execution_timing_mismatch | leaky | **clean (wrong)** | leaky |
| honest_mean_reversion | clean | clean | clean |
| honest_trailing_window | clean | clean | clean |

**baseline: 4/5. advanced: 5/5.** Reproduced identically (same per-strategy verdicts, both binaries) on a second independent live run minutes later -- not a one-off. All 20 trajectories (2 runs x 5 strategies x 2 binaries) are real and in `trajectories/`.

The one miss is the interesting one, and it's a clean demonstration of the whole thesis. `advanced`'s trajectory for `execution_timing_mismatch` shows it forming the *correct* hypothesis before calling the tool ("trades on the same bar's close price movement without a one-bar lag, introducing look-ahead bias"), then getting a huge delta back from `shift_test` (9.413 -> -0.933, delta=10.346) and *initially concluding CLEAN anyway* -- misreading a large delta as "this looks like an honest collapse," exactly the shift-test blind spot documented in Iteration 2. Because that verdict disagreed with `verify::audit`'s empirically-justified rule, the self-correction retry fired, and the model's second pass ("is sharpe_original alone plausible for a legitimate signal here?") reached LEAKY. `baseline`, with no tool and no retry, just kept its first wrong guess. This is `problem.md` §03 step 4 ("if inconclusive, explores an alternative hypothesis") actually happening, not a hypothetical.

- **Decision:** Kept all four fixes. Numbers recorded here are real, not illustrative.
- **Key Insight / Learning:** A near-miss worth stating plainly: the first "clean" 5/5-vs-5/5 result looked like success and was actually a broken experiment -- the giveaway was that it was *too* clean (baseline matching advanced exactly, on a task explicitly designed to be hard for baseline). Suspiciously perfect evaluation results are a signal to audit the evaluation itself, not a result to report. The self-correction mechanism the advanced agent is supposed to demonstrate turned out to be load-bearing for a *real* case in the very first genuine live run, not just the case it was designed against on paper.

### Iteration 6: Prior Art, For Real -- `backtest-audit` Against the Same 5 Strategies

- **Hypothesis:** `problem.md` names `backtest-audit` (a real, installable PyPI package) as the static-analysis prior art this project differentiates against, and quotes its own README's stated limitations. That claim is stronger as a reproduced number than as a citation -- translate all 5 seeded strategies to equivalent Python/pandas and actually run the real tool against them.
- **Implementation:** `eval/prior_art/` -- five pandas translations (`window_mean_reversion.py`, `zscore_reversion.py`, `mean_deviation_crossover.py`, `prior_return_fade.py`, `trailing_mean_fade.py`), each a faithful port of the matching Rust strategy, written so each leaky one's bug mechanism is expressed the way a real developer would actually write it (a centered rolling window; plain-pandas whole-series normalization with no sklearn `.fit(`; execution against the same bar's return) rather than contrived to dodge the tool's rules.
- **Evaluation Evidence:**
  - Installed the real package from PyPI (`pip install backtest-audit`) into a venv, confirmed with a positive control that it correctly fires on its own documented trigger pattern (`df["signal"] = df["close"].shift(-1)` -> `LAB001`, exit code 1).
  - `backtest-audit check .` against all 5 translated files: `✓ No issues found.` Confirmed per-file with `--format json` -- every file, including all three leaky ones, returns `[]`.
  - **backtest-audit: 2/5** (both true negatives; zero true positives on any leaky strategy) vs. this project's own **baseline: 4/5, advanced: 5/5** (Iteration 5).
- **Decision:** Kept as a separate, clearly-labeled comparison (`eval/prior_art/`, Python + a venv), not wired into `cargo test` -- keeps the core Rust reproduction path free of a Python/pip dependency, per `problem.md`'s self-contained-engine goal, while still making the comparison fully reproducible on its own.
- **Key Insight / Learning:** Every one of backtest-audit's three misses traces to a *structural* limitation, not a near-miss or an unlucky pattern choice: two of the three leaky strategies use idioms (`rolling(center=True)`, plain-pandas global stats) that are look-ahead/leakage bugs in substance but aren't the literal syntax its six rules pattern-match against, and the third (execution-timing mismatch) is a whole category of bug none of its rules address at all -- it's not that the rule for that category has a gap, there is no rule for that category. This is the actual, load-bearing version of `problem.md`'s "cannot detect patterns beyond its static rulebook" -- verified against the real tool rather than assumed from its README.

### Iteration 7: A Static-Analysis Tool of Our Own, and a Reliability Finding

- **Hypothesis:** Iteration 6 demonstrated that `backtest-audit`'s specific six rules miss our bug categories -- not that static analysis in general is useless against them. A Rust-native static pass, built for *this* codebase's actual patterns rather than pandas idioms, should catch what `backtest-audit` can't, and should make `advanced`'s hypothesis-formation step genuinely tool-assisted (grounded in a deterministic AST check) rather than LLM intuition alone -- complementary to `shift_test`, not competing with it. Framed explicitly as addition, not replacement: static analysis and empirical verification catching the same bugs from different angles is the point, not a contest between them.
- **Implementation:** `src/static_checks.rs` -- three rules over a real `syn`-parsed AST (not string matching): `SA-EXEC-OFFSET` (an `execution_offset()` override that isn't the honest `1`), `SA-FORWARD-WINDOW` (a window/index bound computed as `i + ...`, reaching forward instead of back), `SA-GLOBAL-STAT` (`.iter().sum()` on the whole series rather than a sliced sub-range). `advanced.rs` now offers **two** tools -- `static_scan` (optional, fast, free) alongside `shift_test` (required, empirical) -- which meant restructuring the tool loop to handle multiple tool_use blocks per turn (the API allows a single turn to call several tools at once) instead of just the first one.
- **Evaluation Evidence:**
  - `static_checks::tests::scan_correctly_classifies_every_seeded_strategy`: **5/5, offline, zero LLM cost** -- every leaky strategy trips exactly the rule matching its actual bug mechanism, zero false positives on the two clean controls.
  - Live re-run of `execution_timing_mismatch` (the strategy that needed a self-correction retry in Iteration 5): this time the model called `static_scan` first, got `SA-EXEC-OFFSET` back, formed a hypothesis explicitly citing it, called `shift_test`, and reached LEAKY correctly **on the first pass -- no retry needed**. Fewer total tokens than the Iteration 5 run that needed the retry.
  - Full `cargo test --test acceptance` re-run: **baseline 5/5, advanced 5/5** this time -- baseline got `execution_timing_mismatch` right, which it had gotten wrong twice before (Iteration 5, reproduced-twice). Its trajectory shows why: still a single unverified guess, no tool, `confidence: "unverified (single LLM call, no empirical check)"` -- it happened to land on the right answer this run. Across 3 live runs total, baseline has now gone wrong/wrong/right on this specific strategy; `advanced` has been right on all 3, every time backed by the same kind of real `shift_test` numbers.
- **Decision:** Kept the static-analysis tool. Reporting the accuracy *pattern* across runs, not just the latest single number.
- **Key Insight / Learning:** A single accuracy number from one run understates the actual gap. `baseline`'s correctness on the hard category is closer to a coin flip than a judgment -- it can't distinguish "I'm right" from "I got lucky," because nothing backs the verdict either way. `advanced`'s verdict is reproducible and inspectable regardless of which way any given run's LLM sampling happens to land, because it's the same real numbers every time. That reliability, not the single-run score, is the actual case for the tool-using agent -- and it's also the reason `verify::tests::shift_test_correctly_classifies_every_seeded_strategy_across_seeds` and now `static_checks::tests::scan_correctly_classifies_every_seeded_strategy` are both offline, deterministic regression tests: the parts of this system that are supposed to be reliable are the parts we can actually prove are reliable, on every `cargo test --lib` run, without spending anything on an LLM call that might just get lucky.

### Iteration 8: Proving Extensibility, Not Just Documenting It

- **Hypothesis:** "Can another person reproduce and extend this" is a real reproducibility claim, not just a determinism one. A short "how to add a strategy" writeup could be wrong in ways nobody notices until someone actually tries it -- a stale field name, a file the registry secretly needs touched twice, a test that turns out to hardcode a count of 5. Actually adding a 6th strategy and running the full offline suite against it is the only way to know the documented steps are really sufficient, not just plausible.
- **Implementation:** `src/strategies/forward_volatility_breakout.rs` -- same off-by-one forward-window bug as `forward_window_lookahead.rs` (Category 1), but computed as a volatility-breakout signal instead of mean-reversion, so it's a genuinely different strategy rather than a copy. Registered as one more `StrategyEntry` in `strategies::mod.rs`. No other file touched: `all_strategies()` is the single registry every test, the `inspect` example, and both binaries iterate, so nothing else needed to know a 6th strategy now exists. Added a `## 8. Extending this` section to `REPRODUCTION.md` documenting the three steps (implement `Strategy`, register one entry, run `cargo test --lib`).
- **Evaluation Evidence:**
  - `cargo test --lib`: **21/21 passing**, with zero code changes to any test file. `shift_test_correctly_classifies_every_seeded_strategy_across_seeds` now covers 6 strategies x 4 seeds = **24/24**; `static_checks::scan_correctly_classifies_every_seeded_strategy` now **6/6**.
  - `cargo run --example inspect`, seed 42: `forward_volatility_breakout` scores `sharpe_original = 0.318`, `sharpe_shifted = 0.554`, `delta = -0.236` -- comfortably under the `1.0` robustness threshold, correctly verdicted **Leaky**, same signature as the strategy it shares a bug mechanism with.
  - `cargo fmt --check` and `cargo clippy --lib --examples`: clean, no changes needed.
  - Live LLM evaluation, run once for real (`gemini-3.5-flash-lite`): `cargo run --bin baseline -- src/strategies/forward_volatility_breakout.rs` -> `VERDICT: LEAKY` (correct). `cargo run --bin advanced -- src/strategies/forward_volatility_breakout.rs` -> `VERDICT: LEAKY` (correct); its trajectory shows `static_scan` fired both `SA-FORWARD-WINDOW` and `SA-GLOBAL-STAT`, then `shift_test` returned `sharpe_original=0.318 sharpe_shifted=0.554 delta=-0.236`, and the model reached the correct verdict on the first pass with no self-correction retry. Both trajectories are real, in `trajectories/`.
- **Decision:** Kept. Registry-based extension really is three steps and nothing else, confirmed rather than asserted -- offline and live.
- **Key Insight / Learning:** The registry pattern (`StrategyEntry` + `all_strategies()` as the one thing everything else iterates) paid for itself here -- the risk with a documented "how to extend" section is always that it quietly omits a step nobody remembers is required (a second registration list, a hardcoded count in a test), and the only way to catch that is to actually do it and watch the offline suite either hold or break. It held on the first try.

### Iteration 9: Uncertainty Reporting -- a Third Verdict for Genuine Tool Disagreement

- **Hypothesis:** `advanced` forced a binary LEAKY/CLEAN verdict even when its own two tools genuinely conflicted -- if `static_scan` flagged something but `shift_test`'s empirical rule came back Clean anyway, the self-correction retry existed specifically to nudge the model toward matching the empirical side, silently discarding the static signal rather than surfacing the conflict. A real disagreement between two grounded tools is different from an unverified guess and should be reported as such: `INCONCLUSIVE`, with a confidence string naming exactly what disagreed, not picked for the model and not quietly resolved by another retry.
- **Implementation:** `verify::AgentVerdict` (Leaky/Clean/Inconclusive) and `verify::combine_signals(static_findings_present, empirical_verdict)` -- pure, deliberately *not* touching `Verdict`/`audit`, which stay exactly as they are (the tested empirical primitive, unchanged). `combine_signals` recognizes exactly one genuine conflict: static positively flagged something, but the empirical rule says Clean anyway (static silence is never a signal either way, per its own documented narrowness). `advanced.rs`'s self-correction retry is now gated on `signal_verdict != Inconclusive`; when it is Inconclusive, the retry is skipped entirely (there's nothing to nudge the model toward) and the verdict is set directly, with a confidence string naming the conflict. `tests/acceptance.rs` gained a third tally (`advanced_inconclusive`, excluded from the accuracy denominator, not counted as a parse failure).
- **Evaluation Evidence:**
  - On the full existing 7-strategy battery, this is provably a no-op: every strategy where `static_scan` ever fires is also empirically Leaky (that's what the locked-in static-checks regression already asserts), so `combine_signals` reduces to today's exact prior behavior in every real case. Confirmed by `cargo test --lib` staying green with zero change to any existing test's expected outcome.
  - New offline fixture, `verify::tests::combine_signals_reports_inconclusive_on_a_genuine_static_vs_empirical_disagreement`: real source text with a harmless `let idx = i + 0;` no-op -- syntactically identical to the shape `SA-FORWARD-WINDOW` pattern-matches on, without the code reaching forward at all -- trips a genuine static false positive via the real `syn`-based `static_checks::scan`. The *actual* logic behind it (mechanically identical to `PriorReturnFade`) runs through the real `shift_test`/`audit` and comes back Clean. `combine_signals(true, Clean)` correctly returns `Inconclusive`. Not a mock of either tool -- both are the real thing.
- **Decision:** Kept. A three-state verdict that's a proven no-op on every real strategy so far, but exercises the disagreement path for real when it does occur.
- **Key Insight / Learning:** The earlier self-correction retry (Iteration 5/7) was designed to fix the model *disagreeing with the truth*; it wasn't designed to distinguish that from the tools themselves disagreeing with each other. Those are different failure modes and deserve different responses -- forcing a pick in the second case manufactures false confidence out of a real, informative conflict.

### Iteration 10: Leak Localization -- Pointing at the Carrier, Not Just Confirming One Exists

- **Hypothesis:** `shift_test` only ever answered "is this strategy's whole feature leaky" -- for a strategy whose feature is built from more than one ingredient, there was no way to say *which* ingredient carries the leak. Generalizing the shift-test to run per named component, reusing its own existing calibrated thresholds, should let the report point at the actual carrier rather than only confirm a leak exists somewhere in the sum.
- **Implementation:** `Strategy::feature_components(&self, bars) -> Vec<(&'static str, Vec<f64>)>`, defaulting to a single `"feature"` component equal to `compute_features`'s own output (a true no-op for every strategy that doesn't override it). `verify::shift_test`'s body was extracted into a pure `shift_test_on_feature(bars, feature, offset)` helper (behavior-preserving refactor, confirmed by the existing 24/24-then-28/28 regression staying green byte-for-byte); `verify::localize` maps it over a strategy's components, reusing `audit`'s existing thresholds directly -- zero new calibration. `forward_volatility_breakout` was decomposed for real into its two actual sub-computations (`forward_mean_deviation`, `forward_std_deviation`); a new fixture strategy, `mixed_signal_reversion.rs`, sums a genuinely honest prior-return component with a small forward-window one specifically to prove `localize` *discriminates* rather than uniformly confirming. `advanced.rs`'s `shift_test` tool now appends a per-component breakdown to its result text whenever a strategy has more than one component (byte-identical output otherwise) -- localization enriches what the tool reports; it does not change the final-verdict decision logic from Iteration 9.
- **Evaluation Evidence:**
  - `mixed_signal_reversion` registered in `all_strategies()` as `is_leaky: true` after empirical tuning (no threshold changes needed) -- correctly Leaky as a whole under the plain existing shift-test/audit (`sharpe_original=3.784`, `delta=2.872`) *and* correctly flagged by `static_checks::scan`, so the whole-battery regressions grew to 7/7 (static) and 28/28 (shift-test across 4 seeds) with zero fallback to an unregistered fixture needed.
  - New offline test, `verify::tests::localize_points_at_which_component_carries_the_leak`: on the real `MixedSignalReversion`, `localize` verdicts `prior_return_component` Clean and `forward_window_component` Leaky -- the concrete, discriminating proof, not just "both flagged."
  - Found and fixed a real spoiler before trusting the live result: the fixture's own component method was first named `forward_leak_component` (and a local variable `leaky`) -- the existing `audit_source` spoiler test caught the variable immediately; the method name (containing "leak" but not the literally-checked word "leaky") slipped past that specific test but is the same category of problem the project renamed every strategy struct to avoid in Iteration 5. Renamed to mechanism-only names (`prior_return_component`, `forward_window_component`) before re-running live.
  - Live run (`gemini-3.5-flash-lite`) against `mixed_signal_reversion.rs`, after the rename: **baseline correct, advanced correct**, and `advanced`'s final answer explicitly cites the per-feature breakdown by name ("the per-feature breakdown specifically pointing to `forward_window_component` as the source of leakage") -- confirmed in the real trajectory, not just the printed summary.
- **Decision:** Kept. Localization ships as an enrichment of the existing `shift_test` tool rather than a new one, keeping the tool surface small.
- **Key Insight / Learning:** The project's own established spoiler-prevention discipline (Iteration 5) isn't a one-time fix, it's a standing constraint every new strategy has to be checked against by hand where the automated test doesn't happen to cover the exact substring -- the existing test caught the variable but not the method name, and only inspecting the actual live model output ("the `forward_window_component` function calculates...") surfaced that the name itself, not just its content, was doing some of the model's work for it.

### Iteration 11: A Second Leakage Axis -- Execution Realism, Proving the Architecture Generalizes

- **Hypothesis:** Every seeded strategy and every verification tool so far perturbs *when* a feature is used -- a temporal axis. The agentic architecture's actual claim (hypothesize, call a tool, verify empirically, reach a verdict) shouldn't be specific to that one axis. A genuinely different bug class -- an unrealistic assumption about what *price* a fill happens at, baked into the PnL calculation rather than the feature -- should be structurally invisible to `shift_test` (which only ever perturbs the feature array) and require its own dedicated empirical tool, wired into the same agent loop, to prove the architecture itself generalizes rather than just accumulating more instances of one bug type. Explicitly time-boxed as the riskiest piece of this batch, with a hard cutoff: ship Iterations 9-10 regardless of whether this one lands.
- **Implementation:**
  - `Strategy::realized_return(&self, prev_bar, bar, position) -> f64` (`src/engine/backtest.rs`) -- honest default (close-to-close, ignores `position`), and a new `run_backtest_with_realized_return` function that sources each bar's PnL from it instead of the market's own close-to-close return. Deliberately parallel to, not a modification of, `run_backtest_from_features` (which `shift_test` depends on for its proven regression) -- `run_backtest`'s single call site was rerouted through the new function and confirmed byte-identical for both of its existing unit tests, since the default `realized_return` reproduces the old behavior exactly.
  - `src/strategies/execution_realism_leak.rs` (`FavorableFillReversion`) -- feature mechanically identical to `PriorReturnFade` (zero temporal leak), but `realized_return` assumes a favorable fill aligned with the position's own direction (bought at the bar's low, sold at the bar's high). First implementation had a real sign bug -- multiplying a positive return bonus by a negative (short) position flips it into a *penalty*, not a bonus -- caught immediately by the strategy's own dedicated test coming back Clean instead of Leaky; fixed by working out the PnL-level algebra properly (subtract the high-close term for shorts, not add it) rather than patching the symptom.
  - `src/verify/slippage.rs` (new `verify` submodule) -- `SlippageTestResult`, `slippage_test` (reruns the strategy's own feature/offset through the backtest once with its declared `realized_return`, once forced to an honest baseline), `audit_slippage` with its own `SLIPPAGE_DELTA_THRESHOLD`, calibrated the same "two clusters with a gap" way `DELTA_ROBUSTNESS_THRESHOLD` was.
  - `advanced.rs` gained `slippage_test` as a third tool, on equal footing with `shift_test` (both are now the harness-forced, always-grounded tools; `static_scan` remains optional). Final-verdict logic now folds slippage into the empirical read *before* checking for a static disagreement: either empirical tool reporting Leaky makes the strategy empirically Leaky, mirroring the "two independent falsification attempts, not a primary/secondary pair" principle the original two-signal `audit` rule already established.
  - `execution_realism_leak` registered in `all_strategies()` as `is_leaky: true`, with a documented, explicit exclusion from the two whole-vector-only regression tests (`verify::tests::shift_test_correctly_classifies_every_seeded_strategy_across_seeds`, `static_checks::tests::scan_correctly_classifies_every_seeded_strategy`) -- it is genuinely, correctly Clean/unflagged on those two axes alone by design; a dedicated test in `verify::slippage::tests` asserts the real, combined claim instead.
- **Evaluation Evidence:**
  - `cargo run --example inspect`: `execution_realism_leak` scores **identical** numbers to `honest_mean_reversion` under the plain `shift_test` (`sharpe_original=1.743`, `sharpe_shifted=-0.529`, `delta=2.272`) -- not just "also flagged Clean" but literally the same numbers, since the feature really is the same mechanism. Confirms the blind spot is real, not approximate.
  - `verify::slippage::tests::slippage_test_catches_the_favorable_fill_leak_shift_test_is_blind_to`: across 4 independent seeds, `shift_test`/`audit` says Clean and `slippage_test`/`audit_slippage` says Leaky for every seed, with a calibration delta of ~4.36-4.64 (measured via a temporary debug print, then removed) against an exact `0.0` for every honest-fill strategy (`slippage_test_is_a_no_op_for_every_strategy_using_the_honest_default_fill`, all 7 other registered strategies).
  - `cargo test --lib`: 26/26 passing, including the sign-bug catch above.
  - Live run (`gemini-3.5-flash-lite`) against `execution_realism_leak.rs`: **baseline correct, advanced correct**. `advanced` called all three tools unprompted in a single turn and its final answer reasoned across both axes explicitly: *"the `shift_test` shows... the feature itself... does not suffer from temporal look-ahead bias. However, the `slippage_test` reveals a massive discrepancy... Because the strategy is leaky on the execution-realism axis, the final verdict is LEAKY."* No self-correction retry needed -- `signal_verdict` matched `model_verdict` on the first pass.
- **Decision:** Kept. The time-box held -- landed within the same session as Iterations 9-10, no scope had to be cut.
- **Key Insight / Learning:** The sign bug is the real story here, not a footnote. `position * realized_return` means any "bonus" added to the return itself flips sign for a short position -- the fix had to work at the PnL level (what should the *dollar* bonus be, for either direction) and translate backward into a return, not be guessed at the return level directly. The project's own established discipline -- a dedicated, real, offline test for every new mechanism, run before trusting a live LLM call -- caught this before a single API dollar was spent verifying the wrong formula, which is exactly what that discipline is for.

### Iteration 12: Verification Pass -- Doc/Reality Drift and a Latent Skip-Logic Bug

- **Hypothesis:** After three feature iterations landed in one session, the docs' specific numeric claims and the code's own edge-case behavior both deserved an audit against reality rather than assumption -- a claim that was true when written can silently rot once the battery grows.
- **Implementation:** Recomputed every numeric claim in `README.md`/`REPRODUCTION.md` from a throwaway harness run against the live registry, then fixed what had drifted. Also fixed a real bug in `tests/acceptance.rs`.
- **Evaluation Evidence:**
  - **Verified correct, no change needed:** shift-test 28/28 across 4 seeds; `static_scan` 7/7; slippage deltas 4.357-4.641 (docs said "~4.36-4.64"); every Sharpe figure in the README's shift-test table matches `cargo run --example inspect` to 2dp; all 41 trajectory files conform to the `agents.md` §4 schema; every registered strategy has both a `baseline` and an `advanced` trace; zero secret-pattern matches in `dev-trajectories/` and across the entire git history; `.env` gitignored and untracked.
  - **Real bug found and fixed:** `tests/acceptance.rs::active_api_key_is_configured` used a bare `.is_ok()`, which is `true` for a set-but-empty `ANTHROPIC_API_KEY=` in `.env`. The test therefore believed a key was configured, ran the binaries, and **failed** instead of skipping -- directly contradicting its own module doc ("skips (not fails) when no API key is configured"). This is the same set-but-empty bug fixed in `src/llm/mod.rs` in Iteration 5; the fix had never been applied to the test's own separate copy of the check. Now mirrors `env_var_nonempty`; verified it skips cleanly with both keys unset.
  - **Doc drift corrected:** README claimed `mixed_signal_reversion` was caught by "ceiling + robust to shift" and that "both signals fire" -- false. Its delta of 2.872 is well above the 1.0 robustness threshold, so only the implausible-Sharpe ceiling fires; the honest half of the sum keeps it genuinely fragile under shift. README's intro still described a two-tool architecture and a loop that only mentioned `shift_test`. `REPRODUCTION.md` told a fresh user to expect `12 passed` (actual: 26) and described the acceptance test as covering 5 strategies (actual: 8); its cost table covered only the original 5, understating a full run by ~60% -- replaced with real measured per-strategy token counts summed across all 8 (31,034 in / 2,159 out). `agents.md` still asserted the crate was "Not yet scaffolded".
- **Decision:** Kept all fixes. The acceptance-test bug is the substantive one -- a graded reproducibility claim that did not hold when actually exercised.
- **Key Insight / Learning:** The same bug class recurred in a second location because the original fix was applied where the bug was *observed* rather than everywhere the pattern existed -- `llm/mod.rs` got `env_var_nonempty`, the test's hand-rolled duplicate did not. Worth noting that the project's own thesis is that unverified claims should be distrusted until empirically checked; that applies to its own documentation as much as to the strategies it audits, and the drift here was found only by recomputing the numbers rather than re-reading the prose.

### Iteration 13: CSV Adapter -- Auditing Backtests This Crate Didn't Author (and a False Positive It Exposed)

- **Hypothesis:** The most-cited limitation of this project in its own docs was that `advanced` can only audit the 8 registered strategies, because `verify::shift_test` takes a `&dyn Strategy`. That looked like a deep architectural constraint. It wasn't: the perturbation underneath operates on a price series and an array of numbers, so the trait requirement lived only in a convenience wrapper -- meaning a backtest written in *any* language could be audited by exporting two columns, with no engine changes.
- **Implementation:** Renamed the private `shift_test_on_feature` to a public `verify::shift_test_features` (the array-level entry point, unchanged behaviour). Added `src/csv_input.rs` (a deliberately small numeric CSV parser: requires `close` plus one or more `feature*` columns, optional OHLCV, clear per-line/per-column errors, no RFC-4180 quoting) and `src/bin/audit_csv.rs` (deterministic, LLM-free CLI with `--execution-offset`, per-column results reusing the localization idea, and its own trajectory output). Added `examples/export_csv.rs` + two bundled example CSVs.
- **Evaluation Evidence:**
  - `tests/csv_adapter_equivalence.rs`: for all 8 seeded strategies, exporting to CSV and auditing that reproduces the Rust-native `shift_test` **bit-for-bit** (exact `assert_eq!` on both Sharpe values, not approximate), and the CSV path independently classifies the 7 temporal-axis strategies correctly on its own.
  - End-to-end: `audit_csv` returns LEAKY on the leaky export (`sharpe=8.357, delta=1.639`) and CLEAN on the honest one (`sharpe=1.306, delta=1.157`); multi-column input correctly separates an honest column from a blatant next-bar-lookahead column (`sharpe=11.516`); `--execution-offset 0` changes the verdict as expected; malformed input errors name the exact line and column.
  - Offline suite: 34/34 (`--lib`) + 2/2 (CSV equivalence), `fmt` and `clippy` clean, new binary's trajectories schema-conformant.
- **Decision:** Kept.
- **Key Insight / Learning:** **Testing the adapter exposed a real false positive in the core `audit` rule, which is the more important result than the adapter itself.** Run against a throwaway random series, it flagged an obviously-honest feature as Leaky. Reproduced deliberately: a structurally honest strategy (only past data, honest offset) keyed to a lag with no real AR(1) signal is misclassified as **Leaky on all 4 seeds** (e.g. seed 42: `sharpe=-0.358, delta=-0.071`). The reason is structural -- the delta signal asks "did shifting destroy the edge?", which is meaningless when there was no edge; a no-edge feature is *trivially* robust to the shift. The seeded battery never caught it because both honest controls have a genuine edge (Sharpe ~1.74), so the blind spot was in our own test design, not just the rule. Pinned as `known_limitation_no_edge_honest_strategy_is_misclassified_as_leaky`, a test that asserts the wrong answer on purpose so it cannot be silently regressed; `audit_csv` guards external data via `NO_EDGE_SHARPE`; `verify::audit` is deliberately left unchanged because v1 is tagged and retuning a calibrated threshold is a v2 decision, not a quiet patch. This is the second time adversarial use, not reasoning, caught this verifier (the first being the one-bar blind spot in Iteration 2) -- which is the project's own Hot Take demonstrated a second time, against itself.

### Iteration 14 (post-v1): Trajectory Self-Certification -- Provider, Model, and a Second Timestamp

- **Hypothesis:** Preparing the demo video surfaced a real gap: nothing in a trajectory file itself proves which LLM produced a verdict, or that a real network round-trip happened at all. `provider`/`model` were known to `llm::Client` internally (it's what picks the wire format) but never surfaced past the call; `started_at` existed but had no paired end timestamp to sanity-check `wall_clock_ms` against.
- **Implementation:** `Client::provider_label()`/`Client::model()` (`src/llm/mod.rs`) expose what the client already knew. `Trajectory::new` (`src/telemetry/mod.rs`) takes `provider`/`model` params; `finish_and_write` now also stamps `finished_at` alongside `wall_clock_ms`. `baseline.rs`/`advanced.rs` construct `Client` before `Trajectory` and pass its real values through; `audit_csv.rs` (no LLM in that path) passes `"none"`/`"n/a (deterministic, no LLM call)"` rather than leaving the fields absent. `agents.md` §4's documented schema updated to match.
- **Evaluation Evidence:** `cargo test --lib`: 34/34, including the telemetry round-trip test now asserting `provider`/`model`/`finished_at`. Live run against `execution_timing_mismatch` with `baseline`: the written trajectory shows `"provider": "gemini"`, `"model": "gemini-3.5-flash-lite"`, and `finished_at` minus `started_at` matching the recorded `wall_clock_ms` (1054ms) to the millisecond. `audit_csv` run against `forward_window_lookahead.csv` confirmed to write `"provider": "none"` correctly, no LLM fields left implying a call that didn't happen.
- **Decision:** Kept.
- **Key Insight / Learning:** This is additive to the schema `agents.md` §4 already documents as "minimum fields," not a breaking change, and every existing consumer (both binaries, the test suite) was updated in the same pass rather than left to drift -- the same doc/reality discipline as Iteration 12, applied proactively this time instead of caught by a later audit.
